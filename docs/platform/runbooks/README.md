# Runbooki operacyjne

Wszystkie operacje na chmurze wykonuje **człowiek** (lub pipeline uruchomiony przez człowieka) – nigdy sesja Claude Code (CLAUDE.md §6).

## first-deployment – pierwsze wdrożenie środowiska
1. **Konta (AWS Organizations):** management, security, log-archive, shared-services, dev, staging, prod. Zastosuj SCP z `infra/cdk/policies/` (najpierw w trybie testowym na OU dev).
2. **shared-services:** repozytoria ECR `bomagent-api`, `bomagent-ingest-worker`, `bomagent-agent-worker`, `bomagent-kb-indexer`, `bomagent-migrate`, `bomagent-llm-gateway` (skan przy pushu, niezmienne tagi, polityka pull dla kont dev/staging/prod) oraz rola OIDC dla GitHub (`vars.AWS_IMAGES_ROLE_ARN`) z prawem pushu tylko do tych repozytoriów.
3. **Konto środowiska:** `cdk bootstrap aws://<konto>/eu-central-1 aws://<konto>/eu-west-1` (**bez** us-east-1: stack WAF wdraża się bez bootstrapu – `BootstraplessSynthesizer`; SCP pozwala w us-east-1 tylko na stack `BomAgent-*-Waf`, WAF, CloudFront i ACM). Potem jednorazowo z laptopa administratora: `pnpm --filter @bomagent/infra exec cdk deploy BomAgent-<env>-Cicd --exclusively -c bomagent:env=<env> -c bomagent:account=<konto> -c bomagent:githubRepository=<owner>/<repo>` (repozytorium jest **wymagane** – rola ufa tylko jemu; jeśli konto ma już dostawcę OIDC GitHub, dodaj `-c bomagent:githubOidcProviderArn=<arn>`;).
4. **GitHub:** środowiska `images`, `dev`, `staging`, `prod`. **Każde** środowisko wdrożeniowe: reguła gałęzi wdrożeń „tylko `main`” (rola ufa środowisku, nie gałęzi); prod dodatkowo wymagane zatwierdzenie. Zmienne: `AWS_DEPLOY_ROLE_ARN` (wyjście stacku Cicd), `AWS_ACCOUNT_ID`, `IMAGE_REGISTRY`; opcjonalnie `DOMAIN_NAME`, `CLOUDFRONT_CERTIFICATE_ARN` (ACM w us-east-1), `ALB_CERTIFICATE_ARN` (ACM w eu-central-1), `ALARM_EMAIL`, `GITHUB_OIDC_PROVIDER_ARN`, `ORGANIZATION_SECURITY_SERVICES=true` (gdy GuardDuty i Security Hub włącza administrator delegowany organizacji – stack nie tworzy wtedy własnego detektora ani huba); na końcu `AWS_DEPLOY_ENABLED=true`. **Prod wymaga domeny i obu certyfikatów** (synth odmawia bez nich: TLS 1.2+ dla użytkowników i HTTPS do ALB).
5. **Bedrock:** w konsoli Bedrock (eu-central-1) włącz dostęp do modeli z katalogu; w `packages/py/llm/src/bomagent_llm/catalog/models.yaml` ustaw `enabled: true` i `verified: true` dopiero po sprawdzeniu, że model działa przez profil EU.
6. **Push na `main`** uruchamia `main.yml`: obrazy (natywnie na runnerze arm64) → `deploy-env.yml` kolejno dev → staging → prod (błąd zatrzymuje dalsze). `tools/deploy.sh`: (a) stack WAF w us-east-1 osobno, jego ARN idzie do stacku Edge jako kontekst `bomagent:webAclArn`; (b) `cdk deploy --all`; przy pierwszym wdrożeniu bez domeny drugi raz stack Identity z adresem CloudFront (callback Cognito); (c) zadanie `dbbootstrap`, potem `migrate`; (d) SPA z `config.json`; (e) smoke.
7. **Baza:** zadanie `dbbootstrap` (jedyne z sekretem użytkownika głównego Aurora) uruchamia `bomagent-migrate bootstrap`: tworzy role `bomagent_migrator`/`bomagent_app`/`bomagent_platform` (bez BYPASSRLS), ustawia ich hasła z sekretów stacku Data, instaluje pgvector, przekazuje bazę `bomagent` (i schemat `public`) migratorowi, nadaje CONNECT rolom aplikacji. Jest idempotentne – uruchamiane przy każdym wdrożeniu. Zadanie `migrate` ma tylko hasło migratora.
8. **SSO (optional, per organisation):** the organisation's owner sets it up in Settings -> SSO (domain TXT record, SAML metadata URL or OIDC issuer/client). The API task role may only manage identity providers of the environment's own user pool. Production needs a Cognito custom domain or the default `*.auth.eu-central-1.amazoncognito.com` hosted domain - the settings page shows the ACS URL and entity id to register at the customer's identity provider.
9. **Pierwszy administrator:** zarejestruj się w aplikacji (weryfikacja e-maila), załóż organizację; hasło ustawiasz sam – nikomu go nie przekazujesz.

## rotate-db-role-passwords
1. W Secrets Manager wpisz nowe hasło roli (pole `password`, tylko litery i cyfry – trafia do URL-a). „Rotate immediately” nie działa: role nie mają funkcji rotacji.
2. Uruchom pipeline (albo samo zadanie `dbbootstrap` z wyjścia `DbBootstrapTaskDefinition` stacku Compute) – ustawia w bazie hasła z sekretów.
3. `aws ecs update-service --force-new-deployment` dla każdego serwisu: ECS wstrzykuje sekrety tylko przy starcie zadania. Między krokiem 2 a 3 działające zadania mają stare hasło – otwarte połączenia trwają, ale nowe połączenia z puli się nie udadzą. Wykonuj poza szczytem i od razu po kroku 2.
Hasło użytkownika głównego Aurora rotuje automatycznie (co 30 dni); `dbbootstrap` czyta je przy każdym starcie.

## rotate-internal-secrets
Klucz bramki LLM i nagłówek `X-Origin-Verify`: zmień wartość sekretu, potem **uruchom pipeline ponownie** – CloudFormation wstawia wartość sekretu do szablonu przy wdrożeniu (dynamiczne odwołanie `{{resolve:secretsmanager}}` rozwiązywane jest tylko, gdy zasób się zmienia), więc jeśli Edge/Listener nie zmieniają się, wymuś to: `cdk deploy BomAgent-<env>-Edge BomAgent-<env>-Compute` z dowolną zmianą opisu lub usuń i odtwórz regułę. Na koniec `--force-new-deployment` serwisów (bramka i API czytają sekret przy starcie). Między krokami nagłówek z CloudFront nie pasuje do reguły ALB → krótkie 403; rób to w oknie serwisowym.

## incident: wiadomości w DLQ
Alarm `*DlqAlarm`: sprawdź logi workera (`/bomagent/<env>/<worker>`), napraw przyczynę, przenieś wiadomości z DLQ do kolejki („Start DLQ redrive”). Przebiegi zawieszone > `run_timeout_s` reaper w API oznaczy jako `failed`.
