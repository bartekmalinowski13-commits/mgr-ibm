# Operational runbooks

All cloud operations are performed by a **human** (or a pipeline started by a human) – never by a Claude Code session (CLAUDE.md §6).

> **Starting out?** One AWS account, dev only: [`single-account-dev.md`](single-account-dev.md). Quick pilot on Supabase + Fly.io (ADR-0017): [`supabase-pilot.md`](supabase-pilot.md).

## first-deployment – first deployment of an environment
1. **Accounts (AWS Organizations):** management, security, log-archive, shared-services, dev, staging, prod. Apply the SCPs from `infra/cdk/policies/` (first in test mode on the dev OU).
2. **shared-services:** ECR repositories `bomagent-api`, `bomagent-ingest-worker`, `bomagent-agent-worker`, `bomagent-kb-indexer`, `bomagent-migrate`, `bomagent-llm-gateway` (scan on push, immutable tags, pull policy for the dev/staging/prod accounts) and an OIDC role for GitHub (`vars.AWS_IMAGES_ROLE_ARN`) with push rights only to these repositories.
3. **Environment account:** `cdk bootstrap aws://<account>/eu-central-1 aws://<account>/eu-west-1` (**without** us-east-1: the WAF stack deploys without bootstrap – `BootstraplessSynthesizer`; the SCP allows only the `BomAgent-*-Waf` stack, WAF, CloudFront and ACM in us-east-1). Then once, from the administrator's laptop: `pnpm --filter @bomagent/infra exec cdk deploy BomAgent-<env>-Cicd --exclusively -c bomagent:env=<env> -c bomagent:account=<account> -c bomagent:githubRepository=<owner>/<repo>` (the repository is **required** – the role trusts only it; if the account already has a GitHub OIDC provider, add `-c bomagent:githubOidcProviderArn=<arn>`;).
4. **GitHub:** environments `images`, `dev`, `staging`, `prod`. **Every** deployment environment: a deployment branch rule "`main` only" (the role trusts the environment, not the branch); prod additionally requires approval. Variables: `AWS_DEPLOY_ROLE_ARN` (output of the Cicd stack), `AWS_ACCOUNT_ID`, `IMAGE_REGISTRY`; optionally `DOMAIN_NAME`, `CLOUDFRONT_CERTIFICATE_ARN` (ACM in us-east-1), `ALB_CERTIFICATE_ARN` (ACM in eu-central-1), `ALARM_EMAIL`, `GITHUB_OIDC_PROVIDER_ARN`, `ORGANIZATION_SECURITY_SERVICES=true` (when GuardDuty and Security Hub are enabled by the organization's delegated administrator – the stack then does not create its own detector or hub); finally `AWS_DEPLOY_ENABLED=true`. **Prod requires a domain and both certificates** (synth refuses without them: TLS 1.2+ for users and HTTPS to the ALB).
5. **Bedrock:** in the Bedrock console (eu-central-1) enable access to the models from the catalog; in `packages/py/llm/src/bomagent_llm/catalog/models.yaml` set `enabled: true` and `verified: true` only after checking that the model works through the EU profile.
6. **Push to `main`** triggers `main.yml`: images (natively on an arm64 runner) → `deploy-env.yml` sequentially dev → staging → prod (a failure stops the later ones). `tools/deploy.sh`: (a) the WAF stack in us-east-1 separately, its ARN goes to the Edge stack as the context `bomagent:webAclArn`; (b) `cdk deploy --all`; on the first deployment without a domain, the Identity stack a second time with the CloudFront address (Cognito callback); (c) the `dbbootstrap` task, then `migrate`; (d) the SPA with `config.json`; (e) smoke.
7. **Database:** the `dbbootstrap` task (the only one with the Aurora master user secret) runs `bomagent-migrate bootstrap`: it creates the roles `bomagent_migrator`/`bomagent_app`/`bomagent_platform` (without BYPASSRLS), sets their passwords from the Data stack secrets, installs pgvector, hands the `bomagent` database (and the `public` schema) over to the migrator, and grants CONNECT to the application roles. It is idempotent – run on every deployment. The `migrate` task has only the migrator password.
8. **SSO (optional, per organisation):** the organisation's owner sets it up in Settings -> SSO (domain TXT record, SAML metadata URL or OIDC issuer/client). The API task role may only manage identity providers of the environment's own user pool. Production needs a Cognito custom domain or the default `*.auth.eu-central-1.amazoncognito.com` hosted domain - the settings page shows the ACS URL and entity id to register at the customer's identity provider. **Warning (SSO review MEDIUM-3):** any CloudFormation update of the `bomagent-web` app client (for example the second Identity deploy with the CloudFront callback URL) resets its `SupportedIdentityProviders` to `COGNITO` only, which disables every organisation's federation while the database still shows the connections as active. Until the automatic reconciliation lands (DECISIONS_LOG), after such a deploy ask each organisation with SSO to save its SSO settings once (Settings -> SSO -> Save), or re-add the `org-*` providers to the client in the console.
9. **First administrator:** register in the application (e-mail verification) and create an organization; you set the password yourself – you do not hand it to anyone.

## rotate-db-role-passwords
1. In Secrets Manager enter the role's new password (the `password` field, letters and digits only – it ends up in a URL). "Rotate immediately" does not work: the roles have no rotation function.
2. Run the pipeline (or just the `dbbootstrap` task from the `DbBootstrapTaskDefinition` output of the Compute stack) – it sets the passwords from the secrets in the database.
3. `aws ecs update-service --force-new-deployment` for each service: ECS injects secrets only at task start. Between step 2 and 3 the running tasks have the old password – open connections persist, but new connections from the pool will fail. Do this outside peak hours and immediately after step 2.
The Aurora master user password rotates automatically (every 30 days); `dbbootstrap` reads it on every start.

## rotate-internal-secrets
The LLM gateway key and the `X-Origin-Verify` header: change the secret value, then **run the pipeline again** – CloudFormation inserts the secret value into the template at deployment time (the dynamic reference `{{resolve:secretsmanager}}` is resolved only when the resource changes), so if Edge/Listener do not change, force it: `cdk deploy BomAgent-<env>-Edge BomAgent-<env>-Compute` with any change of the description, or delete and recreate the rule. Finally `--force-new-deployment` of the services (the gateway and the API read the secret at start). Between the steps the header from CloudFront does not match the ALB rule → a brief 403; do this in a maintenance window.

## incident: messages in the DLQ
Alarm `*DlqAlarm`: check the worker logs (`/bomagent/<env>/<worker>`), fix the cause, move the messages from the DLQ back to the queue ("Start DLQ redrive"). Runs stuck for longer than `run_timeout_s` are marked `failed` by the reaper in the API.
